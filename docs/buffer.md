# Выкладка в TikTok через Buffer

Утром Actions собирает 3 ролика → `pipeline/buffer_publisher.py` отдаёт их Buffer. Режим **`now` (по умолчанию): все ролики публикуются на аккаунт сразу**, без слотов и очереди. Режим `queue` ставит их на **12:00, 17:00 и 21:00 по Asia/Almaty**. Песни вы кладёте в Drive `audio`, больше ничего.

## Настройки (GitHub → Settings → Secrets and variables → Actions)
**Secrets:** `BUFFER_API_KEY`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`.
**Variables:**
| имя | значение | смысл |
|---|---|---|
| `VYBEX_BUFFER` | `now` | рабочий режим. Нет переменной = `now` (ролики публикуются сразу). `queue` = по слотам, `draft` = черновики, только явно |
| `VYBEX_POSTS_PER_DAY` | `3` | сколько роликов собирать и ставить в день (берутся первые N слотов из `config.json → buffer.slots`) |
| `VYBEX_TIMEZONE` | `Asia/Almaty` | часовой пояс слотов |

Переключение draft ⇄ queue = только переменная `VYBEX_BUFFER`, код не меняется. Для разового запуска: Actions → generate → Run workflow → поле **buffer**.

## Режимы
| режим | что делает |
|---|---|
| `off` | ничего не отправляет |
| `plan` | **только чтение**: проверяет канал, видео, свободные слоты и пишет, куда что встало бы. Ничего не загружает и не создаёт |
| `draft` | пост создаётся черновиком (без времени) |
| `queue` | пост создаётся на ближайший свободный слот (`customScheduled` + `dueAt`) |
| `now` | пост публикуется на аккаунт сразу (`shareNow`), время и слоты не используются. Все 3 ролика уходят в одну минуту утреннего запуска. Статус `sending` → `sent`; не `sent` через час = `PROBLEM` в Summary |

Любое другое значение = `off`. Расписание канала в Buffer через API записать нельзя, поэтому время ставится у каждого поста отдельно; расписание в интерфейсе Buffer можно не заполнять.

## Как выбирается время
Слоты 12:00/17:00/21:00. Берётся ближайший свободный слот (не раньше чем через 20 мин). Слот занят, если в ±30 мин уже есть запланированный пост; день полон, если там уже `posts_per_day` постов. Очередь заполнена на сегодня — ролик уходит на завтра и дальше (до 60 дней). Читаются только посты со статусом `scheduled`: **черновики не читаются и не меняются**, команд `editPost`/`deletePost` в коде нет.

## Проверки перед отправкой (любая неудача = ролик не уходит, остаётся в `ready/` и Drive)
- Права: песня из источника с проверенной лицензией, либо файл из Drive с вашей декларацией `VYBEX_OWNER_DECLARES_RIGHTS=1`. Это проверка *декларации*, не самих прав.
- MP4, H.264, 1080×1920, есть аудио (если ролик со звуком), длительность 3–180 с, файл целиком декодируется без ошибок, ≤ 100 МБ.
- Ссылка на хостинге: HTTPS, 200 без редиректа, `video/*`, размер совпадает.
- Подпись из `caption.txt`; отметка ИИ уходит флагами `aiAssisted` и `isAiGenerated`.
- Ролик без звука (режим `tiktok`, музыку добавляете в TikTok) идёт как **уведомление** (`schedulingType: notification`): Buffer напомнит опубликовать вручную, сам ничего не выложит.

## Надёжность
- Повтор: sha256 файла хранится в `Drive/state/buffer.json`. Один файл не отправляется дважды ни в каком режиме (старый тестовый черновик в `queue` заново не уйдёт). Если ответ Buffer потерялся, но пост дошёл, он находится в очереди по тексту и не создаётся второй раз.
- Статус: каждый запуск спрашивает у Buffer статус прошлых постов (`scheduled/sent/error`). `error` или «час после времени всё ещё scheduled» = `PROBLEM` в Summary и красный шаг.
- Повторы запросов: чтение до 4 попыток (429, 5xx, обрыв сети); создание поста повторяется только при 429/502/503/504 и сбое подключения, при неясной ошибке сначала проверяется очередь.
- Ошибки не прячутся: шаг Buffer красный при `error`, `skipped` (нет секретов) и `PROBLEM`. Состояние всё равно сохраняется в Drive, ролики, которые ещё не опубликованы, не удаляются ни с диска, ни из Drive.
- Хостинг: копия в Cloudinary удаляется сразу, как Buffer пометил пост `sent`; остальные (не отправленные) через день после времени поста и старше `keep_days` (7). Черновики не удаляются (вы можете поставить их в расписание позже).
- **Очистка Drive после публикации.** Когда Buffer сообщает, что пост отправлен в TikTok (`sent`), следующий запуск удаляет из Drive `ready/<дата>/<ролик>.mp4`, `caption.txt`, `sync.txt` и саму папку дня (вместе с `report.json`), если в ней не осталось видео. Файлы уходят в корзину Google Drive (около 30 дней, восстановимо). Исходная песня в `done/` остаётся; удалить и её: `config.json → buffer.delete_song_after_sent: true`. Не трогаются черновики, запланированные и ещё не отправленные посты, ролики без звука (уведомления: вы публикуете вручную), старые записи без пути к файлам. Запись о посте в `state/buffer.json` остаётся, чтобы файл не отправился повторно. Ошибка удаления красит шаг и повторяется в следующий запуск. Команда вручную: `python -m pipeline buffer drive-cleanup --state <файл>` (нужен rclone и доступ к Drive).

## Проверка без публикации
1. `python -m pipeline buffer check` (локально, ключ в окружении): канал, пауза очереди, сколько постов в очереди, где окажутся следующие три.
2. Run workflow с `buffer = plan`: всё то же для реальных роликов, ничего не создаётся.
3. Потом `buffer = queue`, `count = 1`: один ролик встаёт на ближайший слот. Откройте Buffer и убедитесь, что время и подпись верны, до выхода поста.

## Пределы
- В Buffer API для TikTok задокументированы только `isAiGenerated` и `title`; приватность, дуэты, комментарии берутся из настроек канала.
- Лимит очереди бесплатного Buffer (около 10 постов на канал) в коде не зашит: при переполнении API вернёт ошибку и она появится в Summary.
- Права на музыку Buffer не проверяет; TikTok может заглушить коммерческий трек.
